Design spec · Ingestion pipeline

Google Drive Sync

A monthly background loop traverses one configured Drive folder, embeds new and changed files through the existing ingestion pipeline, and keeps Qdrant in step. The upload route stays as a Drive-aware test scaffold that requires a drive_id per file. A single-page admin UI wraps the admin endpoints.

§ Overview

Key takeaways

Cadence

Monthly + on startup

Initial scan runs at boot, then the loop sleeps DRIVE_SYNC_INTERVAL_SECONDS between scans (default 2,592,000 s = 30 days).

State

No new database

Sync bookkeeping rides on Qdrant payloads (drive_id, modified_time). Known-file set seeds from a payload scroll at startup — state survives restarts.

Reuse

Same ingest path

Drive files flow through the existing FileIngestionService — identical embeddings to the HTTP upload route, regardless of source.

Auth

Service account only

One configured service account, one watched folder (includes all subfolders). No per-user OAuth, no whole-drive scanning.

End users

Search + open in Drive

Users never see Drive auth, sync state, or admin controls. Results carry source_url linking the original asset; access is gated by Drive's sharing settings.

Admin

Endpoints + admin UI

/admin/sync, /admin/sync/status, /admin/sync/reindex/{id} — all behind ADMIN_API_KEY. Thin single-page UI at /admin/ui.

§ Scope

Goals & non-goals

Goals

  • ▸ Drive is the production ingestion source. POST /v1/file-embeddings stays as a Drive-aware test scaffold — every request must carry a drive_id per file; uploads without one are rejected (422).
  • ▸ The Upload tab and uploadFiles client are removed from the UI; the route stays for scripted tests behind UPLOAD_API_KEY.
  • ▸ Admin can trigger out-of-band sync and inspect state via /admin/sync, /admin/sync/status, or the admin UI at /admin/ui.
  • ▸ Once-per-month interval; initial scan on startup.
  • ▸ Reuse FileIngestionService — embeddings identical regardless of source.
  • ▸ Qdrant payloads carry sync bookkeeping; no new database, no lost state.
  • ▸ End users never see Drive auth, sync state, or admin controls.
  • ▸ Search results carry a source_url to the original Drive asset; opening it is gated by Drive's own sharing settings, not the backend.

Non-goals

  • ▸ Per-user Drive OAuth — service account only.
  • ▸ Multiple folders or whole-Drive watching.
  • ▸ Drive push webhooks (needs public HTTPS + ~7-day channel expiry).
  • ▸ Writing back to Drive.
  • ▸ A polished, multi-page admin app. The admin UI is one static page — key gate, status panel, sync trigger, reindex form. JSON endpoints stay canonical.
  • ▸ OCR for scanned PDFs (existing pipeline limit).
  • ▸ Backend proxying of file bytes or end-user permission checks — Drive sharing settings are the access gate.

§ Discovery

How files are found

Drive's changes.list is whole-drive, so it doesn't fit single-folder scoping. The scanner does a folder traversal instead: 

files.list(q="'<FOLDER_ID>' in parents and trashed=false",
           fields="files(id,name,mimeType,modifiedTime)", pageSize=1000)
traverse into mimeType == application/vnd.google-apps.folder   # subfolders
paginate with pageToken until exhausted

Change detection

Compare each file's Drive modifiedTime against the modified_time stored in the Qdrant point payload.

Deletion detection

Diff the traversal result against the known-ID set, seeded from Qdrant at startup.

§ Configuration

Environment variables

Read once at startup via the existing Settings class. Sync is enabled when both Drive vars are set; otherwise the scheduler never starts and /health reports drive: "disabled".

Variable Required Default Description
DRIVE_SERVICE_ACCOUNT_JSON when enabled None Full service-account JSON as a single env var.
DRIVE_FOLDER_ID when enabled None Single Drive folder ID to watch. All subfolders included. Admin's private folder — never exposed in UI.
DRIVE_SYNC_INTERVAL_SECONDS optional 2592000 (30 days) Sleep between scheduled scans. Initial startup scan always runs when Drive is configured.
UPLOAD_API_KEY optional None Bearer token required for POST /v1/file-embeddings. When unset, the route returns 403. Used only by scripted tests.
ADMIN_API_KEY optional None Bearer token for /admin/*. When unset, admin endpoints return 403. Separate from UPLOAD_API_KEY.

.env.example ships placeholders.

§ Components

Four modules, one new store method pair

drive/client.py

DriveClient

▶

Thin wrapper over googleapiclient.discovery.build('drive', 'v3', ...). Runs in a thread via asyncio.to_thread — googleapiclient is sync, backend rules forbid blocking the event loop.

DriveFile (immutable record):
    drive_id           # Google's file ID
    name
    mime_type
    modified_time      # timezone-aware UTC
    drive_path         # e.g. "Reports/2026/Q1.pdf"

DriveClient:
    traverse_folder(folder_id) -> list of DriveFile
        # folder traversal; skips trashed; files only

    download(drive_id, mime_type) -> bytes
        # native files: fetch raw content
        # Google-native (docs/sheets/slides): export to PDF first

    check_health() -> "ok" | "unavailable"
        # ping via about.get

drive/sync_state.py

SyncState + SyncPlan

▶

Holds the known-ID set plus last-run bookkeeping. No I/O except the Qdrant seed. SyncPlan is immutable: upsert (list of DriveFile), delete_ids (list of drive IDs).

SyncState:
    seed_from_qdrant() -> count
        # scroll all points, collect payload drive_id values

    diff(seen) -> SyncPlan
        # upsert = all seen files (modified_time dedup happens at
        # ingest time); delete_ids = known - seen

    record_upserted(drive_id)
    record_deleted(drive_id)

drive/scheduler.py

SyncScheduler

▶

Async loop. Owns one DriveClient, one SyncState, the ingestion service, and the Qdrant store.

SyncScheduler:
    start()
        # seed state from Qdrant, run initial scan, then sleep loop

    stop()

    tick_once() -> SyncResult
        # one full scan; public so /admin/sync can call it

tick_once per file: read existing Qdrant payload by drive_id; skip when modified_time matches; else download and pass (filename, content type, content, drive path) into the ingestion service with extra payload {drive_id, modified_time}.

Requires new Qdrant store methods find_by_drive_id and delete_by_drive_id (payload-field filter), plus passing extra payload through on upsert.

api/routes/health.py

Health extension

▶

HealthResponse gains drive: str — one of ok unavailable disabled.

/health stays public; the frontend already removed the health badge, so this is for curl/admin visibility only.

§ Admin API

Endpoints & HTTP status codes

All three endpoints sit behind require_admin (bearer ADMIN_API_KEY) and share these codes:

401 · missing bearer token 403 · wrong key 503 · Drive sync disabled
POST /admin/sync

Runs scheduler.tick_once(). Body carries the result even when failed > 0:

{ upserted: int, skipped: int,
  deleted: int, failed: int,
  duration_ms: int }
200 scan completed 409 scan already running
GET /admin/sync/status

Read-only, never fails on Drive state:

{ enabled: bool, running: bool,
  known_files: int,
  last_sync_at: str | null,
  last_result: object | null }
200 always when reachable
POST /admin/sync/reindex/{drive_id}

Fetches metadata + bytes, forces an upsert regardless of modified_time. Returns {reembedded: bool}.

200 reindexed 404 not in folder or Qdrant 409 scan already running 502 Drive API unreachable

Admin auth reuses the bearer pattern from backend/app/security.py. UI page: backend/app/static/admin.html served at GET /admin/ui — no framework, fetch() only, all state server-side.

§ Asset access

Users open the original asset

Search results link back to the original Drive asset. Access is gated by Drive's sharing settings — the backend never proxies bytes or checks permissions itself.

Mechanism

  • ▸ Scheduler stores drive_id on every synced point payload.
  • ▸ _to_search_item derives source_url = https://drive.google.com/file/d/<drive_id>/view when present; null otherwise.
  • ▸ VectorSearchItem gains source_url: str | None.
  • ▸ SearchPanel renders an “Open in Drive” link when present.

images only for now: only image points carry a full payload today (_has_full_payload filters the rest), so only images get a source_url.

Access model

  • ▸ Prerequisite: watched folder shared with the intended audience (workspace-wide or link sharing).
  • ▸ Opening source_url is gated entirely by Drive; users without access see Drive's own 403 / request-access page.
  • ▸ drive_id in the response is an identifier, not a secret — it grants nothing without Drive-side permission.

§ Data flow

One scan, step by step

Scheduled scan — happy path ▶ 
1. start a scan (tick_once)
2. files = traverse the watched folder        # runs in a thread
3. plan = diff(files) against known IDs
4. for each file in plan.upsert:
     existing = look up stored point by drive_id
     if it exists and modified_time is unchanged: skip
     content = download the file
     ingest (name, mime type, content, drive path) with
       extra payload {drive_id, modified_time}
     record as upserted
5. for each id in plan.delete_ids:
     delete stored point by drive_id
     record as deleted

First run

Known-ID set empty (fresh Qdrant) → everything in the folder is upserted.

Restart with data

Seed from Qdrant, so deletions remain detectable across restarts.

§ Failure modes

Error handling

Drive 429 / 5xx

Retry with backoff, 5 attempts inside traverse_folder/download. After exhaustion, abort this tick; next scan retries everything — traversals are idempotent. Never crash the loop.

Drive 401 / 403

Auth failure — log loudly; /health reports drive: "unavailable". Search keeps working on existing Qdrant data.

Per-file ingest fail

Counted in SyncResult.failed; reason surfaces via GET /admin/sync/status. Loop continues with the next file.

Download blip

One retry, then count as failed.

Concurrent scans

tick_once guarded by an asyncio.Lock; POST /admin/sync and POST /admin/sync/reindex/{id} return 409 when busy.

§ Upload route

Drive-aware test scaffold

POST /v1/file-embeddings stays as a Drive-aware test scaffold. Every request must declare the Google Drive ID per file; without it, the upload has no link back to its source and the deletion logic can't identify it.

Contract

  • ▸ Multipart body: one or more files fields with matching drive_id and optional modified_time per file.
  • ▸ Missing drive_id → 422 for that file. modified_time optional, defaults to "now" if absent.
  • ▸ The handler constructs the same FileUpload value the scheduler uses, threading drive_id and modified_time into the Qdrant payload.
  • ▸ Auth: UPLOAD_API_KEY (separate from ADMIN_API_KEY). When unset, the route returns 403.
  • ▸ Response (FileEmbeddingResponse) unchanged.

Why the requirement

  • ▸ Sync identifies files by drive_id; uploads without one become invisible to the deletion logic.
  • ▸ source_url only resolves when drive_id is present; missing it breaks the user link.
  • ▸ FileUpload gains drive_id: str + modified_time: datetime — required for both ingestion paths.

§ Scope tail

Out of scope & open risks

Out-of-scope follow-ups ▶
  • ▸ Push notifications (webhooks)
  • ▸ Multi-folder watching
  • ▸ Per-user OAuth + personalized search
  • ▸ OCR for scanned PDFs
  • ▸ Progress streaming for very large folders

Open risks

Drive API quota

low

Personal-scale folders are far under quota; monthly cadence keeps it negligible.

Large folders

medium

Initial traversal of thousands of files takes minutes; GET /admin/sync/status shows running: true meanwhile.

Google-native exports

medium

Docs/sheets/slides export as PDF and go through the PDF path. Quality depends on export fidelity.
